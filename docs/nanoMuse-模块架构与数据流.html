整体形状：每台设备都是一个完整 Agent

不是“瘦客户端 + 云端大脑”。手机里跑着原生的 Kotlin Agent，语言的执行交给 APK 里的一个 Alpine；桌面里跑着 dsh + Python 手，云端中继只做三件事：账号、路由、可选的模型代理。理解这一点，后面十一层才成立。

读法

先看这张总览图，认住四个物理位置：设备（App 与界面）、本地运行时（Agent 循环与工具）、协同层（Hub 客户端）、中继（账号与转发）。之后每个模块都在这四层里找到自己的坐标；每个模块给两张图——架构图说明“零件如何咬合”，时序图说明“一次调用如何走过”。

图里的连线只画主路径，不画全部可能性；每条连线都有方向，虚线是返回或事件，琥珀色是“需要人点头”的位置。代码引用取仓库真实路径，可以直接对照源码读。

三个不变的结构选择

  • 模型不碰工具。Agent 只把工具调用交给 Sentinel，由后者决定放行、拦截或问人；这条边界贯穿 M03、M05、M06。
  • 一轮对话只有一个装配根。所有单例由 NanoMuseApp 创建，会话线程只共享、不新建；这让换模型、开关 Hands 变成改装配层的一件事。
  • 跨设备传的是“请求”，不是“上下文”。Hub 上跑的是对端自己的 Muse，用对端自己的模型和工具；发起方只保留转写与审批。

M01

客户端外壳：四种形态，一套形状

Android、iOS、桌面、Web 不是四个产品，是同一套交互语言的四次实现：一张脸、一个主会话、若干侧聊、聊天里的审批卡、设备页。每台设备同时扮演两个角色——自己的 Agent，以及别人可以借用的“手和前台”。

它管什么

把人的输入变成一条本地请求，把运行时的事件画成可读的时间线，把“需要你决定”的时刻变成一张卡。它还负责本机的权限：Android 的无障碍服务、macOS 的屏幕录制与辅助功能、文件目录授权。没有这些，后端的工具再强也落不了地。

原理

  • Android 是上游子树 + 自有包。仓库里的 android/ 是 OpenMinis 1.13 的可拉取子树，自有代码只放在 io.github.nanomuse.*；Agent 循环、工具 schema、审批与界面都是 Kotlin 原生，proot + Alpine 只是它手里的那个 Linux（M11、M12 展开）。断网时仍能对话，模型只负责推理。
  • iOS 是纯 Swift 客户端。android/src/ios/NanoMuse/*.swift，账号与模型走 Cloud；Hub 上只实现 info、open、notify、task，screen 明确回 no_screen——不假装自己有一双看不见的手。
  • 桌面是“壳 + 插件”两层。harness/desktop 是 Electron 壳，启动一个 dsh Host 子进程（Node 模式）；真正干活的是 DeepSeek Harness 加插件 harness/dsh-nanomuse。手不是插件自己实现的，而是把 Python 运行时以 MCP 挂进来（nanomuse mcp）。
  • Web 是运行时的自带前门。web/ 用 Vite + React 构建，产物直接提交到 nanomuse/server/static/，由运行时自己的 HTTP 服务托管；浏览器 Demo 则是跑在模拟手机里的同一套界面。
  • 只有三条通道。REST /api 负责命令与状态，WebSocket 负责事件与审批，/v1/hub 负责跨设备帧；客户端不直连数据库，也不直连模型。

M02

装配根：把配置变成一个能跑的进程

nanoMuse 的依赖关系是单向的：配置 → 装配根 → 组件 → Agent。没有全局可变单例被随手 new，也没有 Agent 自己去找模型。这一层决定了“换一个 provider”或“关掉 Hands”只需要改一处。

它管什么

NanoMuseApp 是组合根：它读配置、建目录、按固定顺序创建保险库、四个 SQLite 存储、连接器、技能库、审计、Sentinel、模型客户端、观察器、MCP、本机手、工具集合，最后把工具集合与模型交给 MuseAgent。它不执行任何业务逻辑，只负责让后面每一层拿到的都是已就绪的依赖。

原理

  • 配置是分层的。config.toml 由人写，app-settings.json（<data_dir>/app-settings.json）由 UI 写，后者覆盖前者；Pydantic 在加载时完成类型校验与默认值填充。
  • 创建顺序有含义。日志 → 目录 → Vault → 记忆/目标/提醒/触发 → 日历与通讯录 → 技能 → 审计 → Sentinel（含授权库）→ 模型（含观察器）→ Holds → MCP → 本机手 → 工具 → Agent。后建的东西可以依赖先建的东西，反过来不行。
  • LLM 是可替换的槽位。构造参数允许注入自定义 llm（测试用 MockLLM）；make_llm() 读 provider 与 base_url，工厂决定用哪种协议适配器（M04）。
  • 工具集合按开关拼装。_build_tools() 先放必选项（terminate、ask_user、files、shell、python、web、goals、reminders、triggers），再按 memory.enabled、邮件/日历/通讯录、技能、GUI、Hands、浏览器逐项追加。没开的连接器不会出现在 schema 里。
  • 同一份装配被多个入口复用。serve、chat、run、mcp、daemon 只是装配后的不同外壳；nanomuse mcp 甚至只把 computer_screen/computer_act 以 stdio 暴露给桌面插件。
  • 线程不重新装配。MuseService 给每个会话建 MuseAgent 时，共享同一个 app 的 stores、vault、sentinel、audit，只换 session_file 与 conversation_id。

M03

Agent 循环：一轮任务真正的骨架

这是全项目的心脏：组装一次系统提示，然后反复“问模型—接工具—再问”。看似常见的 ReAct，难点都在边界上——上下文怎么裁、工具交换不能切断、卡住怎么发现、进程被杀后怎么恢复。

它管什么

把一条用户消息推进到最终答复：决定模型看到什么（提示、记忆、目标、近两日日程、设备与技能清单）、能调用什么（工具 schema）、什么时候停（无工具调用、terminate、步数上限、预算超时、卡住）。它不执行工具，也不决定权限。

原理

  • 系统提示每轮重建，而不是缓存。换语言、换记忆、后台目标推进都可能改变提示；中途收到新消息时还会重建一次，让语言规则与记忆跟上最新那句。
  • 窗口是“最近 + 不可切断”。max_context_messages 从尾部取；若切点落在工具交换中间，就向前推到下一条 user 消息；一整轮太长时保留开头的工具交换；图片只留最新 max_context_images 条，历史本身不删图。
  • token 预算是另一道闸。fit_context() 把系统提示、窗口与工具 schema 一起算进去，超限时按策略裁剪，但保留本轮用户请求。
  • 空回复有救。模型只想了没答（finish_reason=length 且 content 与 tool_calls 都空）时，用 roomier_max_tokens()（至少 16k）重试一次；连续两次空回复才收尾。
  • 卡住检测靠签名。最近三条 assistant 的 content + 工具名 + 参数 序列化后完全相同，判定为原地打转，插入一条 STUCK_PROMPT 让它换策略；max_steps 用尽时去掉工具再问一次，强制给结论。
  • 工具图片走 user 消息。工具结果的消息结构不能带图，所以截图作为紧随其后的一条 user 消息（最多两张）；模型不支持视觉时只给文字并明确告知。
  • 会话落盘是原子的。写临时文件 → fsync → os.replace；重启后 _repair_dangling_tool_calls 给没有结果的调用补一条结果，否则 provider 会拒收整段历史。
  • 任务是有预算的。task_budget 按任务继承，记录 token、步数、秒数；超时或超预算时把“为什么停”写成一条 assistant 消息，而不是静默失败。

M04

模型层：把“任意端点”收敛成一种语气

上层只认识 BaseLLM：给一段消息，拿回一段回答与工具调用。底下可能是 OpenAI Chat Completions、Responses API、ChatGPT 登录态、本地 Ollama，也可能是完全没有原生工具调用的小模型。协议差异全部消化在这一层。

它管什么

选择用哪个端点、按什么协议说话、流式怎么切、图片怎么缩、重试怎么做、工具调用用原生还是提示词模拟。它还维护一张能力目录：谁能聊天、谁能看图、谁能生图、谁能生视频。UI 判断“这个功能能不能用”时只查这张表。

原理

  • provider 名解析成“协议 + 地址”。resolve_provider() 先看目录 nanomuse/llm/providers.json；目录条目给出 protocol 与 base_url，factory.py 再据此选 OpenAIChatLLM、OpenAIResponsesLLM 或 CodexLLM（ChatGPT 那条 PKCE 登录链路）。
  • 不支持的端点用提示词补。PromptToolAdapter 把工具写成系统提示，模型输出 <tool_call>{...}</tool_call>，结果以 <tool_result> 用户消息回灌；tool_mode=auto 时先试原生，失败再降级。
  • 流式过滤器负责“分声道”。ThinkStreamFilter 逐块识别 <think>，把推理内容交给 on_reasoning_delta，可见文本交给 on_delta；未闭合的 think 视为推理，不污染正文。
  • 图片在编码前就被压过。长边 1568px、总像素上限 2M、JPEG 编码、按文件缓存；端点一旦拒绝图片内容，vision_available 置为 False，后续只发文字并在原位说明图被略去。
  • 重试是自己的责任。客户端把底层 retry 关掉（max_retries=0），自己用指数退避包住整个流式请求，避免“流到一半断了却当作成功”。
  • 预算在调用点上扣。task_budget.ask() 是所有模型调用的统一入口，辅助调用（整理记忆、生成点子、Sentinel 观察）也计入同一任务，防止后台调用偷偷烧钱。

M05

工具层：模型能碰到的全部东西

工具是 Agent 与世界之间的唯一接口，也是最危险的地方。nanoMuse 把“工具长什么样”和“工具能不能跑”拆成两件事：BaseTool 只描述与执行，权限判断交给 Sentinel。

它管什么

维护工具注册表，把每个工具渲染成 OpenAI function schema；调用时先做参数评估（assess()）生成摘要、风险、警告、目标与出网信息，再交给闸门。它同时负责把 MCP 远端工具、技能脚本、连接器 API、设备屏幕统一成同一种调用形状。

原理

  • 契约是声明式的。每个工具声明 risk、reads_private_data、egress、accepts_secrets；assess(args) 可以按这一次的参数把风险临时抬高，并给出人话摘要——这张摘要就是审批卡上的那一行。
  • 注册表不负责容错。找不到工具时返回一条“unknown tool + 可用清单”的失败结果，而不是抛异常；safe_execute 兜住其余异常，保证一轮任务不会因一个工具而死。
  • 内置族按落点分。文件与 shell/python_execute 落在 workspace 与沙箱；web_search/web_fetch/browser 落在网络与页面；memory/goals/reminders/triggers 落在 SQLite；邮件/日历/通讯录是连接器；skills 是“按需展开的指令包”；coding CLI 把 Codex/Claude Code/Cursor 当子进程。
  • MCP 是首选扩展方式。支持 stdio、streamable HTTP、SSE 三种传输，一个远端工具映射成一个 MCPTool；手机把 App 自身能力挂成 127.0.0.1 的 device server，工具名统一带 device__ 前缀。
  • 技能是文件，不是函数。内置与用户目录各一份，SKILL.md 在对话里按需展开；沙箱把技能目录只读挂进去，所以技能里的脚本与参考资料能在盒子里运行。
  • 手是工具的特例。phone_screen/phone_act/phone_task 与 computer_screen/computer_act 走同一套注册表，但风险按“手指下面是什么字”动态判定（M06）。

M06

Sentinel：模型与真实世界之间的那道门

它不是“内容审核”，而是一套能力授权系统：每个工具调用都要过六步判定，敏感动作停在你面前，凭据永远不进模型上下文，做过的事全部留痕。项目自己的说法很克制——它是同进程里的一个模块，不是云上的沙箱。

它管什么

决定一次调用是放行、询问还是拒绝；决定授权绑定到哪个具体目标、能活多久；在执行前替换保险库占位符、在执行后抹掉结果里的密钥；把整轮会话标记为“已接触私密数据”，从此对外发送要额外确认。

原理

  • 决策顺序是固定的六步。① deny_tools；② 显式 [[sentinel.rules]]（工具 glob + 参数 glob）；③ always_allow/always_ask；④ 风险等级 × 模式（ask/strict/auto）；⑤ 污点：读过私密数据后，向白名单外出网一律询问；⑥ 警告：rm -rf、sudo、curl | sh 只有显式 allow 规则能覆盖。
  • 授权是能力，不是态度。grant key 是 tool:target：web_fetch:example.com、send_email:a@b、shell:git。允许 git 不等于允许 curl；一条管道要覆盖其中每个程序。唯一例外是 shell 的“本轮对话”——一次任务马上要用 ls、wc，逐个问是噪音。
  • 作用域有五档。拒绝、一次、本对话、直到重启、24 小时、始终；后两者写入 approvals.json，可逐条撤销。带警告的调用永远只能“一次”。
  • 污点按会话隔离。读过邮件、日历、通讯录、workspace 外文件、或标记了 reads_private_data 的 MCP 输出后，该会话被标记；只存在内存，重启即失，旁边的会话不受影响。这是对提示词注入最实用的一道防线。
  • 保险库只给连接器用。Fernet 加密的 vault.enc，配置里写 {{vault:NAME}}；内置工具不接受占位符（遇到就拒绝，绝不原样执行）；输出里出现密钥替换为 [REDACTED:NAME]；子进程环境变量按名字模式清洗。
  • Linux 上有真沙箱。bubblewrap 给每次 shell/python_execute 一个独立命名空间：workspace 唯一可写，home 不可见，/tmp 私有，默认只有回环网络；判定需要网络才给网，此时这次调用就算 egress。
  • 观察器只观察。reviewer 用另一个模型给建议（5 秒超时、6000 字符输入），但建议永不授予权限、永不代替人回答审批卡。

M07

长期状态：记忆、目标、提醒、触发

四类“会跨会话活下去”的东西，四种 SQLite 文件：记忆是被动回忆，目标是主动推进，提醒看时间，触发看事件。它们共享一个原则——写入可追溯，冲突可回滚。

它管什么

让 Agent 不必每次从零开始：记住关于人的事实，维护一个带步骤的目标，按时间提醒，按事件触发一次运行，并把这些状态在正确的时间注入系统提示。它还负责清理：合并重复记忆、撤销误记、防止同一提醒重复投递。

原理

  • 记忆表很小，但日志很重。memories 只有 content/category/source/时间；memory_log 记录每次改动的 before/after/reason/restored，所以“整理”可以撤销。写入先做完全相同内容去重。

应用服务：把“一个 Agent”变成“很多会话，一个界面”

Agent 本身是单线程的一次运行；产品要的是主聊天、多个侧聊、后台目标、跨设备任务同时存在而不互相踩。这一层就是调度器：一个线程一个 worker，一个线程一个 inbox，所有线程共享同一套存储与闸门。

它管什么

接收 HTTP 与 WebSocket 请求，维护会话列表与时间线，把 Agent 的回调翻译成前端能画的事件，把审批请求挂起成 future 等前端答复，把定时任务的投递做成至少一次。它还是“产出的文件”能被看见的原因：每轮结束扫描 workspace，把新文件作为 artifact 事件广播。

原理

  • UI 协议是唯一呈现边界。文本增量、assistant 消息、工具调用与结果、Sentinel 通知、ask_approval()、ask_user()。终端是 ConsoleUI，Web 是 WebUI；换一个前端不必改 Agent。
  • 线程是隔离单位。Thread 持有自己的 MuseAgent、inbox、worker、timeline；一个线程忙时，别的线程照常跑。正在运行时收到的新消息进 inbox，在下次模型调用前折叠进当前轮。
  • 审批是挂起的 future。WebUI.ask_approval() 把卡片写进时间线后 await；前端通过 API 解析，future 完成；无人答复则超时（默认 1 小时）按拒绝处理。服务重启时，未决卡片被标为 expired，因为背后的运行已经没了。
  • 时间线写合并但有版本。关闭时强制 flush 最新快照，旧的 worker 晚到的写不能覆盖新快照；重启时把 running 的工具、pending 的审批、live 的浏览器/手部事件修正为真实状态。
  • 落盘三件套。threads/index.json 只存元信息；<tid>.json 是时间线；<tid>.session.json 是模型看到的完整消息历史。三个文件分开，时间线可以很长而不拖慢模型恢复。
  • 对外只用 token。服务默认只监听本机，server_token 在 data_dir；跨设备不靠暴露端口，而靠 M09 的出站连接。

Hub：让每台设备成为另一台的远端

没有端口映射，没有局域网配对。每台设备向中继开一条出站 WebSocket，中继只在同一账号内转发。跨设备只传两种东西：原始动作，和“一整件事”。

它管什么

把账号里的设备组成一个可寻址的集合；让任意设备把命令或任务投给另一台，并跟踪它的进度、审批与终止。它解决的核心问题是“谁来做决定”：命令在发起设备先被判一次，任务里的审批回到提出请求的人手里。

原理

  • 帧很少。hello、welcome、devices、call、event、result，加上 ping、rename、forget、profile、sync、working。设备 id 按安装生成（phone-… / pc-…），web 设备永远不是目标。
  • 动作是原始的。info、shell、files、file.get、file.put、open、screen、notify 立即执行，跳过对端的大脑；命令在“打字的那台设备”先过 ShellGuard 或 Sentinel。
  • 任务是转交的。task {text, conversation, turn_id, stream} 让对端自己的 Muse 在独立会话里跑；过程用 event 的 tool/tool_result/approval/text 回流，发起方的聊天里能看到和对端一样的步骤。
  • 审批回到提问的人。对端的闸门先发 event {stage:"approval"}，发起方弹自己惯用的卡片，approve {approval_id, allow} 回去；对端本地也显示同一张卡，先答先赢。
  • 可靠性靠 id 与对账。调用 15 分钟超时；任务有 turn_id，重复 turn 返回已存状态而不重放；断线后用 task.status 查 accepted/completed/failed/cancelled/interrupted/unknown，不确定就视为“可能已生效”，绝不自动重发。
  • 权限是声明出来的。远程控制开关决定 hello 里 actions 的集合；关掉后只答 info/notify，其余回 not_allowed。凭据与设备 id/kind 绑定：4001 是 key 失效，4003 是被同 id 的新连接顶替。

中继：账号、额度、同步、可选的模型代理

一个 FastAPI 进程加一个 SQLite 文件，官方可以跑，你也可以自己跑。它不做推理编排，只做四件事：证明你是谁、替你转发、在你愿意时转发模型请求、把会话文本同步给你的其他设备。

它管什么

账号与密钥的生命周期、设备注册表、Hub 路由、OpenAI 形状的模型代理、按 token 计费、对话同步，以及运维控制台。它刻意不把“你问了什么”当成默认采集项——只有三个明确开关：同步、保留轮次、客户端事件。

原理

  • 登录是验证码换 key。/v1/auth/code 发 6 位码（阿里云短信或 SMTP），/v1/auth/verify 换 nm_…；同一号码登录第二台设备只多一把 key，不多一份额度。另有密码登录与带 TTL 的 session key。
  • 模型代理是 OpenAI 形状。/v1/models 与 /v1/chat/completions（流式或非流式）由服务端持有上游 key；并发用 CHAT_CONCURRENCY 闸住，排队时用空 choices 的 chunk 告知客户端“在排队”。
  • 计费按上游 usage。ledger 一行一请求，记录模型、token、金额；终身额度加每分钟速率两道闸，防止泄露的 key 被刷穿。
  • 隐私是构造出来的。手机号与邮箱以 HMAC-SHA256 检索，明文用 AES-GCM 加密（密钥由 CLOUD_SECRET 派生）；key 只存哈希；验证码存“带密钥的哈希”，因为六位数直接哈希等于可穷举。
  • 同步有自己的 API。/v1/sync/* 存会话标题、角色、文本、时间、设备与附件元信息（不存文件）；账号级 seq 单调递增，客户端按 cursor 增量拉；删除留 30 天墓碑；单账号上限 20000 条消息、2000 个侧聊、单条 16384 字节。

端侧运行时：一个 APK 里装着一台 Linux

手机端不是“把 Python 服务器塞进 App”。Agent 循环、工具 schema、审批和界面都是 Kotlin 原生的；proot 里的 Alpine 是它伸出去的那只手——命令在这里跑，文件在挂载里看得见，会话之间环境不丢。这一层只解决“能否执行”，不解释“该不该执行”。

它管什么

安装 rootfs、提取 proot、按会话保活一个 shell、把用户选中的目录挂进去、把 DNS 与软件镜像配好，并在每次启动时重新铺一遍随包分发的脚本。它向上只暴露一个入口：ExecutionCoordinator.execute(sessionId, command, timeout)。

原理

  • 一个 APK，一个原生 Agent。android/ 是 OpenMinis 1.13 的子树，nanoMuse 的改动只在 io.github.nanomuse.* 与带 // nanoMuse: 标记的位置。模型调用、工具分派、审批卡、时间线都在 Kotlin 里发生；proot 不是运行时的宿主，而是 shell_execute 的执行器。仓库里确实有过 WebView + Python 服务器的版本，已被归档为设计记录（docs/archive/android-python-line.md），不是今天下载到的这个 App。
  • rootfs 随包走，不联网装。打包时把 alpine-minirootfs 3.21 塞进 assets，首次启动解到 filesDir/alpine-rootfs；解包是手写的 POSIX tar 解析（不依赖设备上的 tar），并用 .arch 记下架构与版本，升级时按此判断要不要重解。
  • proot 也是随包的二进制。proot 与 loader 从 assets 提到 nativeLibDir，LD_LIBRARY_PATH 指向那里。它是进程级的：每条命令一个 proot 进程，没有常驻内核，所以没有“内核崩了整机重来”这种状态。
  • 每次启动重铺一层。default_mount 覆盖到 rootfs：/usr/local/bin 下的 minis-open、minis-mcp-cli 等入口脚本、以及 /etc/profile。这一步保证 App 升级后新脚本一定生效；铺完再重放用户选的软件镜像、按系统当前网络刷新 resolv.conf——否则每次启动都会把镜像选择改回默认。
  • 环境是写死的。PATH、HOME=/root、BROWSER=/usr/local/bin/minis-open（让 webbrowser.open() 落到宿主的打开处理器）、ENV=/etc/profile（非登录 shell 也能读到别名与 HISTFILE）、CHARSET=UTF-8、NO_COLOR、PYTHONDONTWRITEBYTECODE。目标只有一个：同一个脚本在手机与桌面输出一致。
  • 挂载决定边界。/var/minis/{workspace,memory,skills,shared,attachments,offloads,mcp-servers,mounts/<name>} 逐个用 -b 绑到宿主目录；用户在系统文件选择器里选的外部文件夹会先转成真实 POSIX 路径再绑。proot 的 -b 在进程启动时就冻结，所以增删挂载会杀掉当前会话的 shell，下一条命令重新拉起——这是设置页动作，用户不在聊天中，不会被感知。
  • 每会话一条持久 shell。PersistentShell 起一个 /bin/sh，命令写进 stdin，末尾附一个唯一标记，读到标记即收尾并解析退出码。同会话用一把 Mutex 串行，不同会话各自一把、可并发；进程死了下条命令自动重建。工作目录、环境变量、apk add 装的包因此能跨命令保留。
  • 时间预算是显式的。默认 900 秒，timeout 上限也是 900；另有 delay 参数——等待期不占 shell，另一个会话仍可执行。超时与中断由 ShellTimeoutPolicy 与 ExecutionCoordinator 一起处理。

端侧工具框架：三类工具、一条桥、三道闸

模型看到的是一份扁平的 schema，实际落到三种物理位置：Kotlin 进程内、Alpine 里的命令、以及被 execve 截走的原生能力。中间那座桥让最后一种看起来像普通命令；三道闸决定哪一步需要人点头。

它管什么

按当前能力拼出工具清单，校验参数，把调用分派到正确的执行器，把结果压回对话，并在需要时弹一张卡。它同时负责把 Android 的系统能力（日历、通讯录、通知、定位、无障碍、Shizuku……）包装成沙箱里可执行的 CLI。

原理

  • schema 是按能力拼的，不是固定菜单。AgentTools.makeAgentTools() 永远给 shell_execute、file_read、file_write、file_edit、browser_use；只有“主模型能看图或有视觉组”才给 read_image；关闭记忆时 memory_write 与 memory_get 直接从 schema 消失——模型连尝试的机会都没有。共 8 个内置工具。
  • 三条执行路径。① 进程内 Kotlin：文件、图片、浏览器、记忆，直接读写绑定目录或 WebView；② Alpine 命令：shell_execute 经 ExecutionCoordinator 进持久 shell；③ offload CLI：命令里出现 android-calendar 这类名字时，执行被截获，转给 App 里的 handler。目前注册了 24 个 handler。
  • 桥的机制是“改写一次 execve”。guest 里执行 execve("android-calendar", argv, envp)，proot 扩展把 argv/env/cwd 通过抽象 Unix socket 发给 App；handler 同步跑完，把输出写进 guest 的 /tmp 文件，回一个 (exit_code, path)；扩展再把这次 execve 改写成 /bin/cat <tmpfile>——于是命令看到的就是普通标准输出，管道、重定向、$? 全部照旧。socket 名带包名（io.github.nanomuse.app.native-offload），被占用时退到每进程一个名字，避免与同装的 OpenMinis 抢同一个抽象命名空间。
  • MCP 不直连，走沙箱里的客户端。servers.json（/var/minis/mcp-servers/servers.json，Claude Desktop 同格式）是唯一真源，App、文件浏览器、沙箱三方共读一份；真正连服务器的是 guest 里的 minis-mcp-cli（stdio / HTTP / SSE）。系统提示只列前 20 个启用的服务器名与一句 note，具体工具体靠模型自己 minis-mcp-cli tools <server> 去发现。
  • Skills 是文件，不是接口。SKILL.md 挂在 /var/minis/skills/<id>/，提示里只给名字、最多 1024 字的描述和真实路径；模型需要时才 file_read 读正文。读 SKILL.md 会记一次使用，用于排序与统计。
  • 闸一：ShellGuard 静态判。把命令按 ;、&&、||、换行拆成管道，再按 | 拆成简单命令，剥掉 sudo/env/timeout/nice 这些包装器，只问四件事：删不删、发不发、付不付、装不装。最强的那条结论胜出；sh -c、python -c、heredoc 会递归或按内容判；/tmp、/var/tmp、/dev/shm 里的删除不算。
  • 闸二：RiskGate 一张卡。六类风险 SAFE / INSTALL / DESTRUCTIVE / OUTBOUND / REMOTE / MONEY 归成三档：安装只通知、删除/外发/远端要确认、付钱最高。五种结局 ALLOW_ONCE / ALLOW_SESSION / ALLOW_ALWAYS / DENY / TIMEOUT；180 秒没人回应按拒绝。付款每次都问，想“记住”必须用锁屏确认，且只能绑定一个对象。
  • 闸三：OffloadGate 三态。每个 CLI 入口都过同一套 BYPASS / ASK_ONCE / NOT_ALLOWED，授权按聊天会话隔离（MINIS_CHAT_SESSION_ID），换会话不会继承上一次的“本会话允许”。
  • 屏幕与远端是两种“手”。nanomuse-hands 需要四件套：Android 11+、无障碍服务、悬浮窗、一个能看图的模型；感知只有截图，无障碍只做手势、截屏和定位输入框，遇到密码框直接拒绝。nanomuse-pc 让手机指挥账号里的电脑（run / ls / get / put / open / screen），命令同样先过 ShellGuard，卡在手机上弹。

M13

一条任务怎么跑完：回合循环、排队与并行

任务不是“一次请求一次回答”，而是一个最多 200 轮的自循环：每轮问一次模型，模型要工具就执行、把结果回灌，再问；直到它不再要工具。手机端真正的并发单位是会话，不是一个会话里的多条消息。

它管什么

接住三个方向进来的任务（人、定时器、别的设备），决定这一次是立刻跑、排队、还是先压缩上下文；跑的时候维护历史、预算、工具轮与落库；跑不完时留下可恢复的尾巴，而不是把界面卡死。

原理

  • 三个入口，一条循环。① 界面：ChatScreen → ChatViewModel.sendMessage()；② 定时：ScheduledTaskAlarmReceiver → ScheduledAgentRunner，目标分 new（新会话）/ follow-up（追加到旧会话）/ rerun（从某条用户消息重跑）；③ 别的设备：hub 的 task → HeadlessChatRunner，会拿到一张 turn_id 回执。三条最后都进入同一个 runAgentLoop()。
  • 进门先过三道检查。正在流式 → 不拒也不抢，排进队列（QueuedPrompt，界面上是一条“待发送”气泡）；正在压缩 → 直接回一句“等压缩完成”；上下文接近上限 → 先压缩再发（自动）或弹一句问（手动）。
  • 一轮干什么。for (turn in 0 until MAX_AGENT_TURNS)，上限写死 200。每轮顺序固定：清洗历史 → 确定性裁剪（prepareContext，不改已存的历史）→ 预算检查（超了就就地压缩并把这一轮作废重来）→ 请求模型（流式）→ 有 tool_call 就执行、把 tool_result 回灌 → 模型不再要工具就正常退出。
  • 撞到上限不是崩，是“可继续”。finalizeAtTurnLimit() 把流式标记收掉、写一条说明“到 200 轮停了”，并打开 canResume，人可以接着让它跑；这与“报错”是两种状态。
  • 落库是增量的，不是最后一次性。流式文本按块追加，工具块一出现就建（tool_start / tool_input / tool_complete 三个通道各自去重），消息与 parts 写进会话库。进程被杀时，InterruptedTailDetector 认得出“半截回复”并给出重试提示。
  • 多任务有三层，但没有全局调度器。① 会话内：一把 _isStreaming 锁，同一时刻只有一轮；② 跨会话：每个 sessionId 一个 ChatViewModel（共享 ChatViewModelStore），所以两个会话可以同时跑，AgentForegroundService 按 sessionCount 保活，切到后台也不断；③ 跨设备：hub 的任务走 headless 通路，与本机人的对话互不阻塞。
  • 排队消息在“轮与轮之间”变成新回合，不插进当前轮。injectQueuedPromptsAsNewTurn() 在当前助手气泡收尾后开一条新气泡；插不进去（比如已经空转）就退回正常调度，队列不会被一条坏消息卡死。
  • 停止是显式的。界面 cancelStream()；远端的 stop 带 turn_id；两者都走 HeadlessTurn.stop 的同一套收尾，保证“停了也要把已有部分落库”。

M14

互操作：MCP、Agent 到 Agent、App 能力

模型要够到三种外部世界：MCP 服务器、账号里的其它设备、这台手机的系统能力。三者的入口、契约与边界完全不同，混在一起讲最容易失真——分开看，它们各自只有一句话。

它管什么

把“模型想做的事”接到正确的外部世界，并在接上去之前把边界说清楚：MCP 走沙箱里的客户端、设备之间走 hub 的 RPC、系统能力走命令行。它不定义新协议，只决定每种能力用哪条既有通道。

原理

  • MCP 的契约是“配置 + 命令行”，不是 schema。servers.json（/var/minis/mcp-servers/servers.json，Claude Desktop 同格式）是唯一真源，支持 command（stdio）、url（HTTP/SSE）、env、headers、启动超时；MCPRepository 负责解析、导入导出、启停，并按会话记一份覆盖（mcp.db），换会话不继承。OAuth 令牌单独存在 McpOAuthTokens 里，不进配置文件。
  • MCP 不在工具表里，是为了省上下文。系统提示只列前 20 个启用服务器的名字和一句 note；真正的工具发现与调用由 guest 里的 minis-mcp-cli 完成（tools <server> 列表、call 传 JSON）。好处是几百个 MCP 工具不占 schema；代价是模型要多敲一次命令。
  • 设备之间是自建 RPC，不是标准 A2A。hub 的动作表是固定的 13 项：info / shell / files / file.get / file.put / open / screen / notify / task / task.status / approve / stop / approve.any。前八项是能力级（在对方机器上跑一条命令、读写一个文件、开一个链接、截一张屏），task 是任务级：把一整件事用自然语言交给对面的 Agent，在对面开一个新会话跑，事件流式回传。
  • 审批留在执行侧，不留在发起侧。别的设备要动这台手机，RiskGate 会在这台手机上弹 REMOTE 卡，授权绑定对方设备 id（“只允许 Desk 这一台”），可一次、可始终；连 task 跑起来以后的每一步工具调用，也仍然走本机自己的闸。总开关是“允许被其它设备操作”，关掉后除 info 全部拒绝。
  • 任务级转交有回执，也有终止。task 返回 turn_id，之后可以用 task.status 查进度、stop 取消、approve 代答本机卡片（approve.any 是“任意设备都能答”的变体）。单次调用超时 10 分钟，比 shell 的 900 秒更宽，因为它包的是一整轮任务。
  • 反向也有：手机当指挥端。nanomuse-pc（reach）把账号里的电脑列进提示，手机可以 run / ls / get / put / open / screen，甚至把整件事用 task 甩给电脑；这正是 A2A 的双向形态，只是没有协议文档，只有一张动作表。
  • App 能力没有走 App Functions API，走的是 PATH。代码里没有任何 AppFunction 适配层；15 个 android-*（闹钟、日历、剪贴板、通讯录、设备、定位、通知、打开、相册、播放器、朗读、语音、天气、无障碍、Shizuku）和 5 个 minis-*（打开、会话、模型、配置、定时）都是 CLI：--help 是文档、stdout 是 JSON、权限不足回 permission_denied。它们靠 /usr/local/bin 里的 17 字节 stub + execve 改写接到 Kotlin handler。
  • 这套选择的代价很明确。零 schema 成本、任意组合、和 shell 天然一致（管道、$?、重定向都能用）；但模型必须先读 --help，参数校验靠 CLI 自己，错误只能从 JSON 里读。这是“用文档换上下文”的交易。

M15

Harness 的模块清单，与把它搬出 Android

端上的 Agent Harness 不是“一个循环 + 几个工具”，而是十四块彼此咬合的部件：会话、提示、预算、模型、工具、闸、沙箱、互操作、保活、观测。想把这套 runtime 搬到别的宿主，能搬的是其中十一块，搬不动的是 Android 给的那三样东西。

它管什么

把“模型 + 工具 + 文件 + 闸”组织成一台能连续干活的机器：谁持有会话、谁装配提示、谁管预算、谁执行、谁批准、谁保活、谁记录。模块之间的依赖是单向的——上层知道下层，下层不知道上层。

组织方式

  • 进程：一个 APK，四条线程面。主线程只做 UI；Dispatchers.IO 跑回合循环与流式解析；沙箱进程（proot + Alpine）在独立 OS 进程里；offload server 是一条本地 socket 线程。它们之间没有共享内存，只有文件、socket 和回调。
  • 服务：保活与可见性。AgentForegroundService 在跑任务时把进程钉在前台，通知里写“正在跑几个会话、当前在干什么”；ScheduledTaskAlarmReceiver 用系统闹钟唤醒，不依赖进程常驻。
  • VM：会话是状态边界。一个 sessionId 一个 ChatViewModel，历史、_isStreaming、队列、草稿、附件都在这层；UI 只是它的一个观察者，headless 通路是另一个观察者，二者共享同一个实例（否则会出现“后台在跑、前台看不到”）。
  • 依赖方向是单向的。UI → VM →（提示 ∥ provider）→ 工具 → 闸 → 沙箱 / offload → 文件与库。反过来只有事件回调（流式块、审批结果），没有下层直接调 UI。
  • 可搬的十一块。回合循环、上下文维护、提示装配、provider 调用与 SSE 解析、工具 schema 与文件类工具、三道闸、offload 注册表、hub 客户端、定时、保活抽象、观测。它们只依赖 JDK + HTTP + JSON。
  • 搬不动的三块。① execve 改写——它依赖 proot 的扩展点，普通宿主没有这个钩子；② Android 系统能力——无障碍、Shizuku、通知、相册、SAF 目录授权；③ WebView 浏览器——browser_use 的标签页、cookie、截图都长在 Android WebView 上。
  • 替代方案要成对出现。沙箱换 bwrap（Linux）或 sandbox-exec（macOS）或容器；execve 钩子换成“PATH 里放同名 wrapper 脚本，脚本 curl 本地端口”——语义上等价于 offload，只是多一次进程启动；WebView 换成 Playwright；系统能力换成一个 DeviceBridge 空实现，缺哪补哪。
  • 分期比一次性搬更现实。M0 冒烟（provider + 一轮循环 + 文件读写），M1 工具与闸（含 shell），M2 上下文与压缩，M3 互操作（MCP / A2A / 设备桥），M4 保活与观测。先让“一句话 + 一次 shell”跑通，再谈沙箱隔离——顺序反了会一直在修沙箱，而不是在修 Agent。

抽出来：把端侧 runtime 做成一个没有界面的后台组件

要的不是“手机 App 的一份拷贝”，而是它里面那个能连续干活的核：一个进程接一个任务，装配提示、调模型、跑工具、过闸、吐事件、落盘。界面、通知、WebView、无障碍全都不进来。

它管什么

以库或进程的形式被调用：给一个任务与会话 id，它自己跑完 200 轮以内的循环，把每一步变成结构化事件，把结果落到会话库；中途要人点头时向外发一条审批请求，没人答就按拒绝走。

为什么抽得出来

  • 循环本身不依赖 UI。runAgentLoop() 只用到六样东西：provider、历史消息、工具表、闸、沙箱、落库与事件回调。Android 里它们被塞在 12,820 行的 ChatViewModel 里，旁边还挂着 Compose 状态、气泡、滚动、附件、草稿——抽的动作就是把这六样收进一个 SessionState，把其余留在 UI。
  • 已经有先例。HeadlessChatRunner 就是“不开界面跑一轮”的现有实现：它按 sessionId 取到同一个 VM，直接调 prompt()，事件走回调。这说明无界面运行在架构上是成立的，只是还借用了 VM 这层壳。
  • 抽走的边界是三个接口，不是一堆文件。Sandbox（执行 + 超时 + 串行）、ApprovalGate（问人 + 超时即拒绝）、EventSink（结构化事件）。Android 侧分别是 proot 持久 shell、RiskGate 卡片、ChatViewModel 的流式回调；换宿主只换这三个。
  • 能带走的是七样。循环、工具表与四个基础工具、静态闸、provider 客户端、会话存储、事件写盘、审批策略——这些只依赖 JDK、HTTP 与 JSON，我在本机用 Kotlin 2.0.21 + JDK 11 编出了可执行 jar，跑通了冒烟。
  • 带不走的是三样。proot 的 execve 钩子（决定 24 个 android-* handler 怎么被“看见”）、Android 系统能力（无障碍、Shizuku、通知、相册）、WebView。后台形态里它们要么换成宿主能力，要么留空。
  • 后台形态下，并发模型反而更简单。一个会话一个 SessionRuntime（单飞行 + 队列），多会话用线程池；取消是一个中断位，不需要 Compose 的协程作用域。默认超时照旧：shell 900s、审批 180s、回合 200。
  • 事件是唯一的输出面。一行一个 JSON（turn_start / turn / text / tool_start / tool_result / approval / loop_detected / done / error），可以直接 tail -f，也可以在前面套一层 SSE 或 WebSocket 给上层 UI。这样“要不要界面”不再影响内核。
  • 冒烟跑的是真链路。脚本化模型端点 → 第 1 轮 file_write 落盘 → 第 2 轮 shell_execute 读到两行 → 第 3 轮收尾；另一场景把命令换成 rm -rf，闸判 DESTRUCTIVE，无人应答即 TIMEOUT，工具返回错误而不是执行。3 轮 / 360 prompt tokens / 243ms。
  • 接回真模型只需换一个类。骨架里的 provider 是非流式的一次调用；Android 原实现是 SSE 增量 + tool_call 按 index 拼装。接口已经留了 onText 回调，补上增量解析即可，循环与工具层不用动。

数据怎么流转，怎么存

把前面十六层叠起来看一次完整往返：一条消息从屏幕出发，经过调度、提示装配、模型、闸门、工具，最后变成三个文件的增量与两行审计；如果它跨设备，还会多出一段中继路由。下面这张总时序图可以逐步播放。

三条通道，各走各的

  • REST /api：命令与状态。发消息、改设置、答审批、取文件。同步阻塞，返回 JSON。
  • WebSocket：事件流。文本增量、工具步骤、审批卡、artifact、状态变化。只向前端推，不承载命令。
  • /v1/hub：设备间帧。动作、任务、进度、审批、profile 与同步提示。出站连接，中继只路由。
  • 第四条是隐性的：模型请求。本地运行时直连你配置的端点，或经中继的 /v1/chat/completions；这条路上走的是提示词全文，所以它决定“什么离开了设备”。

一次写的顺序

用户消息先入会话文件与审计，再进模型窗口；模型回复先成为内存消息，再流给前端，最后随会话原子落盘。工具结果先过脱敏，再进消息。审批卡先写时间线，再挂起 future。没有跨库的强事务：时间线与会话文件是两份独立快照，靠轮次与合并规则保持一致。

invariants
  • 会话文件：临时文件 + fsync + rename
  • 时间线：新版覆盖旧版，关闭时 flush
  • 投递：source_key 唯一，先 claim 再发
  • 同步：seq 单调，客户端持 cursor
  • 审批：未答复超时即拒绝

一句话总结存储策略：会话与时间线是“每会话一份的文件快照”，长期状态是“四个职责单一的 SQLite”，跨设备是“中继上的文本副本加本机的原文件”，而凭据与审计是“只进不出”。这套设计换来的不是强一致，而是可解释：任何一个数字都能在某个文件或某张表里找到出处。

这套结构的代价

  • 同进程闸门不是 VM 隔离。Sentinel 与 Agent 在同一个进程里；在没有 bubblewrap 的平台上，被批准的 shell 拥有与你相同的权限。项目文档自己写明了这一点。
  • 三份状态需要对齐。会话 JSON、时间线 JSON、同步库各自演进，靠轮次 id、消息 id 与 cursor 对齐；断网与重启的边角情况是测试重点。
  • 桌面是两个运行时的拼装。dsh 负责循环与界面，Python 负责手；一处配置错位（NANOMUSE_PY、MCP 挂载）就会表现为“手不见了”。

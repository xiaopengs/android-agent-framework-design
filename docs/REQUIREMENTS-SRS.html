1 文档说明

1.1 编写目的

本文定义一套运行在 Android 端侧的 Agent Framework 的产品与工程需求。这套框架负责把"一句话任务"变成"一串可审计的动作"：接收任务、装配提示、驱动模型、调度工具、通过安全闸、在受限环境中执行、把每一步写进会话库与事件流，最后交出结果。

文档面向研发实现、测试验收与架构评审三类用途，同时作为后续移植（把内核抽成无界面组件）的需求基线。文中凡描述现有实现行为之处，均来自对 nanoMuse 项目 Android 端的源码级拆解，不是推测；凡属目标数值之处，均以"目标"标注，需在验收阶段实测。

1.2 范围与边界

纳入本需求范围的包括：任务接入与会话管理、回合循环与上下文预算、提示装配、工具框架、风险判定与审批授权、执行沙箱、互操作（MCP、设备间动作、App 能力 CLI）、事件与存储、可脱离界面的后台运行形态，以及端云协同的路由决策与通信总线。

不纳入：界面视觉与交互设计、应用商店分发与签名、云端多租户与计费、模型训练与微调、iOS 与桌面端实现、MCP 服务器与具体业务 Skill 的内容本身。上述内容如需要，属于相邻需求，不在本文验收范围内。

1.3 读者对象

产品与架构人员关注第 2、3 章的范围、目标与模块边界；客户端研发关注第 4、7、8 章的功能条目、接口与数据；测试人员以第 9 章验收标准为主，并参考第 5 章的时序与异常分支；安全与合规人员关注 4.4 节的三道闸与第 8 章的数据留存。

2 产品概述

2.1 背景

Android 上的 Agent 应用常被误认为"在容器里跑一个 Python 运行时"。对 nanoMuse 的源码拆解给出了相反的事实：Android 端的 Agent 循环、工具 schema、审批逻辑与界面全部由 Kotlin 实现，工程内共 727 个 Kotlin 文件、约 22.9 万行代码；proot 与 Alpine 根文件系统只承担 shell 命令执行器的角色，历史上那套 WebView 加 Python 服务的实现已归档，不再是主线。

这一事实决定了端侧框架的形态：核心是 Kotlin 的回合循环与工具调度，容器只是一个可替换的执行后端。也正因如此，这套能力可以被抽出来、在没有界面的进程里独立运行——项目内已有的无界面运行入口就是先例。

2.2 目标

G1 可运行：一个任务从接入到收尾能完整跑通，包含工具调用、风险判定、人工审批与结果回灌。

G2 可替换：执行后端、审批通道、事件出口、会话存储四类依赖可整体替换，而内核代码不做改动。

G3 可审计：任意一次工具调用都能回答四个问题——谁在什么时刻要求做什么、是否经过审批、批的人是谁、结果如何。

G4 可移植：内核不依赖 Android 界面框架，可在后台服务、命令行或服务端进程中以同一份代码运行。

2.5 约束与假设

运行环境：Android 11（API 30）及以上；AArch64 为主，armv7 需另行提供根文件系统。

许可约束：上游为 GPL-3.0-or-later，任何分发形态需履行相应义务，内部使用不影响。

3 总体架构与模块划分

3.1 分层视图

端侧框架自上而下分四层：接入层负责把所有来源的任务收敛成同一种任务对象；会话与循环层负责隔离、排队、装配提示并驱动模型；能力层提供工具、闸与互操作；运行时层提供执行环境、存储与事件出口。四层之间是单向依赖：上层可以调用下层，下层不得反向依赖上层。在端侧四层之前，端云协同还叠加 RootRouter 路由决策层与 CloudAgentBus 通信总线层，其设计见 3.7 节。

跨层约束有三条：接入层不得直接调用沙箱，必须经由循环与闸；能力层不感知执行后端是 proot 还是宿主进程；运行时层不含任何提示词逻辑，提示装配只发生在会话层。这三条是"可替换"与"可移植"两个目标的实现前提。

3.3 与宿主应用的边界

框架以库或后台服务的形式被宿主应用调用。宿主负责四件事：保证进程存活、提供通知与前台服务、申请并授予系统权限、承载用户交互界面。框架自身不弹任何界面：需要人点头时，它通过审批接口向宿主发一条请求，宿主渲染成卡片或命令行提示，再把决定回传。

这条边界带来一个直接收益：同一套内核既可以在带界面的 App 里跑，也可以在没有任何界面的进程里跑。判断实现是否符合要求，只需检查内核代码里是否出现 Android 界面类或 Activity 的引用。

3.4 一次任务的运行框架

一次任务在框架内固定经过六个步骤，这六步是后续所有时序与需求的骨架。

第 1 步 · 接入。四个入口把任务包装成统一对象：会话标识、任务文本、附件、触发来源。同一会话已有回合在跑时，新任务进入队列而不是并发。

第 2 步 · 装配。载入该会话历史，按稳定段与易变段装配系统提示，依据设备能力注册工具，然后进入循环。

第 3 步 · 循环。请求模型；若返回工具调用则分派，若无则本轮收尾。轮次上限 200，撞上限不算失败，而是置为"可继续"。

第 4 步 · 判定与审批。工具执行前先过静态判定，得出风险类别；需要人介入时发审批请求，超时按拒绝处理。

第 5 步 · 执行。在沙箱内执行命令或调用宿主能力，结果规范化后先落库、再回灌给模型。

第 6 步 · 收尾。模型不再请求工具时结束，写出最终文本、轮次数、令牌用量与结束原因；事件流同步关闭。

3.5 Agent Loop 回合循环内核设计

3.5.1 定位与内部组成

Loop（回合循环内核）是框架中与平台无关的推理往复引擎，只负责“请求模型—解析工具调用—执行并回灌—判断收尾”，本身不包含界面、不实现系统能力、也不承担端云路由。其内部由六个协作部分组成，各部分通过明确的数据对象交互，彼此不反向依赖。

3.5.2 单轮消息流

每一轮的处理顺序固定，不可调换，尤其“先裁剪预算再请求模型”必须成立。

  • 载入该会话历史与待处理追加消息，恢复上一轮的工具调用与结果对应关系。
  • 执行确定性裁剪并检查上下文预算；超限先裁剪，仍超则压缩，压缩期间该轮作废重来。
  • 按稳定段、易变段、运行时上下文三段装配提示，并附上当前可用工具表。
  • 携带工具表向模型发起请求；回收文本增量与结构化工具调用。
  • 若返回工具调用，逐个执行：参数校验 → 风控闸门 → 审批（如需）→ 执行 → 结果规范化 → 先落库再回灌。
  • 若无工具调用，进入收尾；存在工具结果则封装为 tool 消息进入下一轮。

3.5.3 终止条件与状态

Loop 的终止原因统一收敛为五类，对应可持久化的会话结束状态；撞上限与打转属于受控收尾，不是异常崩溃，已产生的工具结果与消息照常落库。

3.5.4 消息模型与回灌约束

  • 消息角色分为 system、user、assistant、tool 四类；tool 消息必须携带 tool_call_id 与工具名，与 assistant 的工具调用一一对应。
  • 工具结果必须先落库再回灌模型，保证“模型看到的”与“库里存的”一致，进程崩溃后可按库内记录重放。
  • 模型侧可见截断标记、错误码与风险拦截原因，便于其更换参数或换一条路径重试。

3.5.5 并发与取消

同一会话同一时刻只有一个回合在跑。取消通过中断位实现：取消当前流式请求并结束本轮，在途工具按超时终止其子进程；已经落库的工具结果不回滚、不重复执行。

3.6 端侧 Runtime 运行时设计

3.6.1 定位

Runtime 是承载 Loop 在 Android 后台持续运行的宿主壳：负责进程与后台服务、线程与并发、会话实例、资源目录、执行后端与事件出口。Loop 内核与工具代码不引用任何 Android 界面类；Runtime 把平台差异收敛到一组可替换接口之后，使同一内核既能在带界面的 App 内运行，也能在无界面进程中运行。

3.6.2 进程与线程模型

  • 一会话一运行时实例，实例之间不共享可变状态，只共享进程级线程池、存储连接与沙箱内核。
  • 会话内单飞行；跨会话并行；全局并发上限可配置（默认 2 个会话并行），超过上限的任务排队等待。
  • 后台形态以无界面 Service 或常驻进程承载，支持“一条任务一次运行”与“常驻服务接收任务”两种用法。

3.7 端云协同设计

3.7.1 总体结构

端云协同在 Loop 之前增加两层：RootRouter 协同调度层负责路由决策，CloudAgentBus 通信总线负责端与云之间的信封编解码、传输与分发。所有请求必须先经 Router，禁止旁路直连本地 Loop。三层职责为：Router 决策目标，Bus 传输与投递，本地 Loop 与云端 Agent 服务各自闭环执行。

3.7.2 RootRouter 路由决策

入口提交统一请求对象，包含原始 Query、是否允许本地、是否允许云端、是否偏好本地与用户 SLA。Router 结合网络状态、本地工具依赖识别、隐私与延迟要求、SLA 判定路由目标 LOCAL / CLOUD / HYBRID，并为本次任务生成全局 traceId 与会话 sessionId。

  • 离线运行、隐私敏感或低延迟要求的任务 → LOCAL。
  • 不依赖本地独占工具且允许使用云端的任务 → CLOUD。
  • 需要云端大模型规划拆解，且执行中包含本地独占工具的任务 → HYBRID。
  • 硬约束：只要命中 10 个本地独占工具之一，Router 不允许进入纯 CLOUD 分支。

3.7.3 CloudAgentBus 通信总线

端与云之间的所有往来统一为信封（AgentEnvelope），字段包括：envelopeId、traceId、sessionId、direction（TO_LOCAL / TO_CLOUD）、msgType（QUERY / STREAM_CHUNK / TOOL_CALL / TOOL_RESULT / STATUS / ERROR / ACK）、routerTarget、seq、isStream、payload 与 meta（时间戳、超时时间）。总线负责 ACK、失败重试、死信、流式分片与按 sessionId 订阅。

  • 上行：本地执行结果、状态与错误封装为 TO_CLOUD；下行：云端规划结论与工具调用封装为 TO_LOCAL。
  • 总线按会话订阅投递，本地队列与云端通道分别对接本地 Loop 与云端 Agent 服务。

4 功能需求

本章按九个模块逐条给出功能说明、行为规则与异常处理。每条功能在 4.10 节汇总为总表，编号与优先级以总表为准。

4.1 接入与会话（M1）

4.1.1 功能说明

框架对外只有一个任务概念，但入口有四个：界面会话、定时任务、远端转交、后台命令行。四者进入内核后被规整为同一结构，因此后续的装配、循环、审批、落库只有一份实现。定时入口有三种目标——新建会话、续接上次会话、重跑上次任务；远端入口要求在受理瞬间返回一个任务号，作为对端的查询凭据。

进门先过三道检查：该会话正在流式输出时，新消息进入队列；该会话正在压缩上下文时，直接拒绝并说明原因；上下文接近上限时，先压缩再发送，或询问用户是否新开会话。三道检查的顺序不可调换，否则会出现"压缩中又插入新任务"的竞态。

4.1.2 行为规则

  • 任务对象至少包含会话标识、任务文本、附件列表、触发来源四个字段；缺会话标识即拒绝受理。
  • 同一会话串行：已有回合在跑时不得并发启动第二个回合，只能入队。不同会话之间可并行。
  • 队列按到达顺序先进先出；出队时机固定在两个回合之间，作为新的回合注入，不打断正在执行的工具。
  • 停止语义是取消当前流式请求并结束本轮；已经产生的工具结果照常落库，不得回滚。
  • 每条消息落库时记录触发来源，便于事后区分"人发的"与"定时/远端发的"。

4.1.3 异常与降级

进程被杀时，会话库中最后一轮可能只有请求没有结果。框架需在下次载入时识别这种未完成尾部，标记为中断而不是显示为正常回复，并允许用户选择继续或丢弃。压缩期间收到的新任务必须明确拒绝，不允许静默丢弃。

4.2 回合循环与上下文（M2）

4.2.1 功能说明

循环是框架的心脏，形态是一个有界 for 循环：轮次从 1 到 200。每一轮的顺序固定——清洗历史、按确定性规则裁剪、检查上下文预算、请求模型、若有工具调用则执行并把结果回灌、若无则正常退出。顺序不可调换，尤其"先裁剪再请求"必须成立，否则预算检查失去意义。

提示装配分三段：稳定段（基础人格、风险政策、能力说明）内容不变，可被模型侧缓存；易变段（技能片段、MCP 服务器摘要、命名补充、媒体与算力说明、会话追加、记忆片段、用户文件片段）每轮重建；运行时上下文（日期、时区、语言、可用模型数量）单独成段，避免污染缓存。

4.2.2 行为规则

  • 单任务最多 200 轮；达到上限时执行收尾流程，状态记为"可继续"，不得报错或丢弃已有结果。
  • 工具结果必须先落库再回灌模型，保证"模型看到的"与"库里存的"一致，崩溃后可重放。
  • 预算检查发现超限时，先做确定性裁剪（丢最旧的工具输出、截断大文本），仍超则压缩，压缩期间该轮作废重来。
  • 同一工具加同一参数连续出现 3 次即判定打转，中断循环并向用户说明，避免无效消耗。
  • 单轮工具调用数设上限（建议 8 个），超出时提示模型收敛，而不是无限执行。

4.2.3 异常与降级

模型返回空内容、返回格式非法、或工具名不存在时，本轮记为失败但不终止任务，最多重试两次后以"无法继续"收尾并附最后一次错误。压缩失败时放弃压缩、按裁剪后的历史继续，并降低后续轮次的上下文预算。

4.3 工具框架（M3）

4.3.1 功能说明

工具表不是固定清单，而是按设备能力拼出来的：shell 执行、文件读、文件写、文件编辑、浏览器这五个永远下发；设备具备视觉模型时才下发读图工具；记忆功能关闭时，记忆类工具整体消失。这样做的目的是让模型看到的工具集合与设备真实能力一致，减少"调了但用不了"的无效轮次。

工具执行有三条路径：进程内 Kotlin 直接调用、容器内命令、以及通过重定向机制转给宿主的命令。三条路径对模型完全透明，模型只看到一个工具名与一份参数，返回的永远是同一套结构化结果。

4.3.2 行为规则

  • 每个工具包含名称、说明、参数 schema、执行体四部分；说明长度受统一预算约束，避免挤占上下文。
  • 参数按 schema 严格校验，缺必填项或类型不符时返回参数错误，不得猜测补全。
  • 执行结果统一为：是否成功、结果码、标准输出、标准错误、是否截断、耗时；截断时保留头尾并提供原文落盘路径。
  • 新增工具只需实现工具接口并注册，不得修改循环代码；这是"可扩展"的验收点。
  • 模型请求不存在的工具时，返回"工具不存在"并附当前可用工具名，不执行任何兜底逻辑。

4.3.3 异常与降级

工具执行抛出未捕获异常时，转换为失败结果回灌，错误信息保留类型与消息但去除堆栈中的绝对路径。工具执行超时按失败处理并终止其子进程，避免僵尸进程累积。

4.4 安全与授权（M4）

4.4.1 功能说明

三道闸串联在工具执行之前。第一道是静态判定，对命令做结构化拆解后回答四个问题：是否删除数据、是否向外发送、是否涉及支付、是否安装软件；拆解要能穿透管道、递归的解释器调用（如再包一层 shell 或 Python）、以及多行内嵌脚本。第二道是风险分级，把命令归为安全、安装、破坏、外发、远端、资金六类，再映射为三档处置：仅提示、需确认、最高级别确认。第三道是按会话隔离的卸载调用授权，只对"转给宿主的命令"生效。

审批有五结局：本次允许、本会话允许、永久允许、拒绝、超时。超时固定为 180 秒，超时即拒绝。资金类每次都问，"永久允许"必须经过锁屏确认这类强认证。被拒绝也要把结果回灌给模型，让它换一条路，而不是静默失败。

4.4.2 行为规则

  • 闸必须在执行前生效，任何工具都不得绕过；工具的"内部实现"调用也要过闸。
  • 审批决定与具体参数绑定；参数发生变化时原授权失效，必须重新审批。
  • 会话级授权只存内存，进程结束即失效；长期授权落 grants.json，并与设备绑定。
  • 危险动作的判定结果、审批人、决定与时间必须写入事件流，不可只记在内存。
  • 远端转交任务的审批在任务执行端本机弹出，不得在对端弹出或静默放行。
  • 仅提示档（NOTICE）也要留痕，只是不阻塞执行。

4.4.3 异常与降级

审批界面不可用、用户长时间未响应、通知权限被拒时，一律按拒绝处理并告知模型"人工通道不可用"。静态判定自身出错时按最高风险处理，宁可多问一次，不可放行。

4.5 执行沙箱（M5）

4.5.1 功能说明

沙箱提供的是一个最小可用的 Linux 环境：根文件系统随安装包分发，首次启动解压到应用私有目录，并用一个架构标记文件记录版本，升级时不覆盖工作区。每次启动都要重放一次覆盖层——把命令入口与登录脚本替换成框架自己的版本，再刷新域名解析；随后把工作区、记忆、技能、共享、附件、卸载缓存、MCP 配置等目录以绑定方式挂进容器。

命令执行按会话复用一条 shell，用标准输入写入命令、用唯一结束标记判断输出结束；同一会话内的命令串行，不同会话之间可以并发。会话的 shell 意外死亡时重建，必要时退化为"一次命令一个进程"的兜底模式。

4.5.2 行为规则

  • 环境变量采用固定清单：命令搜索路径、家目录、浏览器入口、登录脚本、字符集、颜色开关、字节码缓存开关，不得由用户输入拼装。
  • 默认命令超时 900 秒，可按会话配置，但不得超过 900 秒。
  • 目录绑定在会话启动时冻结；运行中增删挂载必须先结束当前会话，不允许热改。
  • 根文件系统解压必须校验完整性与架构，架构不符时拒绝启动并提示，不得带着残缺环境运行。
  • 命令输出超过阈值时截断，并把完整输出写入工作区文件，返回其路径。

4.5.3 异常与降级

解压中断、磁盘不足、绑定失败时，沙箱进入不可用状态，此时所有需要执行的工具返回"环境不可用"，而文件读写在宿主侧仍可工作，保证会话不至于整体崩溃。

4.6 互操作（M6）

4.6.1 功能说明

互操作解决"工具从哪来"和"任务能交给谁"两个问题。工具来源有三类：设备内置（含系统能力）、MCP 服务器、技能包。任务去处有两类：同设备的不同会话，以及另一台设备。

MCP 以一份与主流桌面客户端同构的配置文件为单一真源，界面只做导入导出，避免出现"配置在数据库里、改不到"的情况；系统提示里只列前 20 个服务器名与备注，防止提示膨胀。设备间通道是一套自建 RPC，动作集固定为 13 个，不在表内的动作一律拒绝；其中转交任务的动作会创建新会话、立刻返回任务号、把流式事件回传，并把审批留在执行端。App 能力则以命令行形式暴露：每个能力一个命令，帮助文本即文档，标准输出为 JSON，权限不足统一返回固定错误码。

4.6.2 行为规则

  • MCP 配置解析失败时，保留原文件并禁用该服务器，不得清空用户配置。
  • MCP 工具调用失败要区分"服务器未启动""认证失效""调用超时"三类，分别给出可操作提示。
  • 设备间动作必须校验来源设备，未配对设备直接拒绝；任务转交必须绑定设备标识。
  • 任务转交超时 10 分钟，超时后对端可查询终态，不得无限挂起。
  • 技能目录只读挂载；技能描述有长度上限，正文按需读取，不预加载全部内容。
  • App 能力命令必须遵循统一契约：帮助即文档、输出即 JSON、错误码固定。

4.6.3 异常与降级

对端离线、网络抖动、认证过期时，任务转交失败并回滚到本机执行或明确失败，不产生"两边都在跑"的重复执行。MCP 服务器不可用时，相应工具从工具表移除，模型侧看到的能力集合相应缩小。

4.7 事件、存储与观测（M7）

4.7.1 功能说明

事件流是框架唯一的对外输出面：任务开始、轮次开始、文本增量、工具开始、工具结果、审批结论、循环结束、错误，共七类。结构化到"一行一个 JSON"，既可以直接被日志系统消费，也可以在前面套一层推送服务转成实时流。

存储采用增量写入：工具开始时写调用记录，参数确定时写参数，结束时写结果，三个通道按调用标识去重，保证崩溃后重放不会出现重复工具块。会话与消息分表存放，工具块单独成表，避免单行过大。

4.7.2 行为规则

  • 每条事件必须带序号与时间戳，序号在会话内单调递增，供断线续传与去重使用。
  • 落库先于事件发送：先持久化，再对外通知，保证"看到的"不会比"存下的"更超前。
  • 密钥、令牌、完整个人信息不得进入事件流与日志；需要排查时以引用标识代替原文。
  • 会话可导出为完整轨迹文件，包含每轮的请求摘要、工具调用与审批结论。

4.7.3 异常与降级

磁盘写满或数据库损坏时，事件降级为仅内存缓冲并告警，会话继续运行但标记"不可恢复"。事件外发失败要重试并有上限，超过上限后丢弃并记录丢弃数量，不得阻塞内核。

4.8 后台形态与 Runtime（M8）

4.8.1 功能说明

把内核从界面里抽出来，靠的不是复制文件，而是把依赖收敛成一组可替换接口：模型客户端、执行环境、审批通道、事件出口、会话存储。Android 端这五者分别是模型 SSE 客户端、proot 持久 shell、审批卡片、视图模型回调、本地 SQLite；后台形态则可以是任意 OpenAI 兼容端点、宿主进程或容器、命令行提示、事件文件、JSONL 存储。换宿主只换这些实现。

可搬走的是七样：循环、工具表与四个基础工具、静态闸、模型客户端、会话存储、事件写盘、审批策略。搬不走的是三样：拦截系统调用并改写的钩子、Android 系统能力、以及网页视图。后台形态里，前两者分别换成宿主能力与"留空即可"，后者根本不需要。

4.8.2 行为规则

  • 内核代码不得引用 Android 界面类、活动、视图模型；以纯 JVM 运行是硬性验收项。
  • 宿主能力（通知、通讯录、日历、定位等）以工具形式注入，不通过系统调用钩子实现。
  • 事件是唯一输出面：上层要实时进度就读事件流，不得反向依赖内核内部状态。
  • 命令行形态必须支持"一条任务一次运行"与"常驻服务接收任务"两种用法。
  • 并发模型简化为：一会话一运行时，单飞行为列，多会话用线程池；取消用中断位实现。

4.8.3 异常与降级

宿主进程退出时，正在执行的命令要先终止再退出，避免留下孤儿子进程；事件文件必须刷盘，保证崩溃前的记录可读。审批通道缺失时默认拒绝，不允许"无人值守自动放行"。

4.9 端云协同（M9）

4.9.1 功能说明

RootRouter 是全部请求的唯一入口，在本地 Loop 与云端 Agent 服务之前完成路由决策；CloudAgentBus 是端云之间唯一的通信通道，所有请求、流式分片、工具调用、工具结果、状态与确认都以信封形式经总线收发。Router 与 Bus 都不承载业务推理，只做决策、传输、分发与回执。

三种调度模式覆盖不同场景：LOCAL 全程本地闭环；HYBRID 由云端规划、端侧执行本地独占工具；CLOUD 由云端全权处理。模式选择在请求受理瞬间确定，执行过程中可按网络状况降级，但不得在两端同时重复执行同一任务。

4.9.2 行为规则

  • 所有请求必须先经 RootRouter 决策，再由 Bus 投递；不存在绕过 Router 直连本地 Loop 或云端的旁路。
  • 命中本地独占工具白名单的任务，Router 不得判定为纯 CLOUD；离线状态下强制 LOCAL。
  • 信封字段齐全：envelopeId、traceId、sessionId、direction、msgType、routerTarget、seq、payload、meta 缺一不可。
  • 总线对每条信封返回 ACK；发送失败按策略重试，超过重试上限进入死信并记录，不静默丢弃。
  • HYBRID 模式下，云端 TOOL_CALL 经 Bus 投递本地，本地结果封装 TOOL_RESULT 回传；两端风控逻辑一致。
  • 跨端任务审批留在执行端本机；任务号可查状态、可停止；超时 10 分钟后可查询终态。

4.9.3 异常与降级

网络中断或云端不可达时，可降级为本地闭环的任务在事件流留痕后转 LOCAL；无法在本地完成的部分明确失败并回滚到本机，不产生"两端都在跑"的重复执行。总线断线重连后按 seq 续传，已确认信封不重发；云端鉴权失效时按错误类型分类提示，不把令牌写入信封或日志。

5.4 并发与多任务规则

框架的并发模型分三层。会话内是单飞行：同一会话同一时刻只有一个回合，这是为了避免两份历史同时被改写。跨会话是多实例：每个会话一个运行时，彼此不共享可变状态，只共享进程级资源（线程池、数据库连接、沙箱内核）。跨设备是并行：转交给另一台设备的任务在那台设备上独立运行，通过任务号查询状态。

本版本不要求全局队列、优先级与抢占。但要求提供一个可配置的全局并发上限（默认 2 个会话并行），超过上限的任务排队等待，避免多任务同时压满内存。这一条是相对现状的补强项，列入 P1。

7 外部接口需求

7.1 模型接口（IF-01）

采用 OpenAI 兼容的对话补全接口：请求包含系统提示、消息数组、工具定义数组与流式开关；响应按流式增量返回文本与工具调用。要求支持工具调用协议、支持中断（客户端断开即停止计费与生成），并在超时或限流时返回可区分的错误类型，供上层决定重试或降级。

7.2 工具接口（IF-02）

工具以"名称 + 说明 + JSON Schema 参数 + 执行函数"四件套定义。执行函数接收参数对象与执行上下文（会话标识、工作目录、取消信号、审批回调），返回统一结果结构。说明字段受长度预算约束；参数 schema 必须能表达必填项、枚举与上限，便于模型一次写对。

7.3 MCP 接口（IF-03）

支持三种传输：标准输入输出、HTTP、SSE。配置以单一文件为真源，字段与主流桌面客户端同构（服务器名、传输类型、命令或地址、参数、环境变量、是否启用）。运行期允许会话级覆盖，但覆盖数据与真源分离存放。认证令牌单独存储，不写入配置文件。

7.7 RootRouter 接口（IF-07）

RootRouter 是全部请求的唯一入口。入参为统一请求对象：原始 Query、是否允许本地、是否允许云端、是否偏好本地、用户 SLA；出参为按会话订阅的信封流（Flow<AgentEnvelope>），流式返回过程与最终结果。Router 内部决策枚举为 LOCAL / CLOUD / HYBRID。

本地独占工具白名单固定为 10 个：shell_execute、file_read、file_write、file_edit、read_image、browser_use、memory_write、memory_get、android_calendar、android_notify。请求依赖上述任一工具时，Router 不得路由到纯 CLOUD 分支；离线状态下强制 LOCAL。决策依据（网络状态、工具依赖、隐私与 SLA）需写入事件流，便于事后复核路由结论。

7.8 CloudAgentBus 接口（IF-08）

总线对外提供两个原语：发送信封（send，返回发送结果，自动完成 ACK、重试与死信处理）与按会话订阅信封流（subscribe，返回该 sessionId 的信封流）。端云往来统一为信封，关键字段如下：

  • envelopeId：信封唯一标识；traceId：全局链路 ID；sessionId：会话 ID。
  • direction：TO_LOCAL / TO_CLOUD；msgType：QUERY / STREAM_CHUNK / TOOL_CALL / TOOL_RESULT / STATUS / ERROR / ACK。
  • routerTarget：LOCAL / CLOUD / HYBRID；seq：会话内单调序号；isStream：是否流式分片。
  • payload：消息体；meta：时间戳、超时时间等元信息。

总线必须保证：ACK 与重试可观测；流式分片按 seq 顺序投递；断线重连后按序号续传，已确认信封不重发；超过重试上限的信封进入死信并记录，不静默丢弃。
